# SPS 日程与物院社团预约互通

## 使用

- 任务日历叠加其他社团的公开活动，显示社团、活动名、起止时间和地点；不加载课程，不重复展示预约页的 SPS 活动。公开范围与预约页一致，为北京时间今天至两个月后的对应日期（含）。前台随任务同步检查，最短间隔30秒；可点“更新”。网络失败保留上次结果并显示提示。
- 主任务开启持续时段后，可选择“暂不设置 / 设置地点”。地点最多80字，默认“未定”。当前正式 SPS 社团的所有未归档持续任务都会同步为预约页的 SPS 活动；旧任务也会首次补齐，子任务和仅截止时间任务不发布到预约页。
- 修改名称、起止时间或地点会更新原活动；归档或关闭持续时段会撤下活动，恢复归档会重新出现。标记完成不撤销活动时段。跨日按北京时间分段，午夜结束不占次日；超出预约页窗口的任务保留源数据，进入窗口后自动显示。
- 同步块在预约页不可单独取消，详情提供原任务入口。手动预约、其他社团记录和课程原样保留。同步反映已经发布的 SPS 安排，允许与现有活动重叠；预约页普通新增仍检查所有手动和同步活动的冲突。
- “导出我的日程 .ics”只导出当前成员负责的未结束持续活动及未完成的截止事项（含子任务）。持续活动导出起止时间、地点；截止事项为不占用时段的单点事件。其他成员独有任务、已归档任务、已结束活动不导出。文件是快照，后续变动需重新导出；重复导出保持稳定 UID，是否更新或重复导入由日历软件决定。

## 连接和数据边界

SPS Worker 保留原 Durable Object `sps-club-service-v1`；预约 Worker 保留 `club-booking-production`，没有重建或迁移数据库。

SPS 配置 `BOOKING_CLUB_ID` 精确绑定正式 SPS 社团，`BOOKING_SYNC_URL` 固定指向预约 Worker 的 `/api/integrations/sps`。预约配置 `SPS_CLUB_ID` 必须相同。随机共享密钥分别保存在 Workers Secrets `BOOKING_SYNC_KEY` / `SPS_SYNC_KEY`，不放在前端、仓库或日志。其他社团即使使用 SPS 名称也不能向此连接发布。

任务写入和 SQLite `booking_sync` 待发送版本在同一事务中提交。Durable Object alarm 在后台发送全量活动快照，失败按15秒至1小时退避重试，页面关闭不影响重试；没有待发送版本时不设定时任务。只有明确返回合法 `sourceVersion` 才记为送达。接收端同一原子写保留手动预约和课程，单调版本忽略重试和旧请求，并通过现有 WebSocket 通知预约页。

发送字段仅为任务 ID、活动标题、起止时间、地点与源版本；不发送任务说明、成员名单、完成记录、账号或邀请码。公开 `/api/activities` 只输出活动，不含课程。前端 CSP 只增加既定预约 API 来源。

受同一服务密钥保护的 `GET /integrations/booking` 提供运行状态；未配置社团时只列出社团 ID 和名称，供部署时选择明确绑定。`POST /integrations/booking` 对已配置社团安排初次补齐/重新检查。此接口只经原 SPS Worker 管理地址使用，不添加到公众网关路由。

上线顺序：设置两个服务的密钥 → 发布接收端 → 发布已绑定社团的发送端 → 调用一次补齐 → 核对原手动预约和课程未变 → 发布两边 Pages 前端。不要用历史 uniCloud/D1 数据覆盖现有预约存储。

## 验证依据

SPS：100 项 JS 测试、44 项 Worker 集成测试、3 项网关测试；预约：74 项 Node 测试、TypeScript 与12项 SQL 冲突检查。新增覆盖跨日和午夜、地点保留/清除、个人选择、ICS 注入转义及 UTF-8 折行、同社团精确隔离、失败重试、持久化、归档/恢复、旧快照、手动数据保留、活动冲突和 WebSocket。

本地双页面实测：从 SPS 页面创建10:00–12:00、地点“物理楼301”的活动，预约页无需手动刷新出现相同 SPS 块和来源入口；SPS 日历显示另一社团15:00–17:00活动。导出按钮成功生成个人日程并显示2项反馈，文件格式由单元测试验证；原生文件保存受锁屏环境影响，未验证系统日历实际导入。
