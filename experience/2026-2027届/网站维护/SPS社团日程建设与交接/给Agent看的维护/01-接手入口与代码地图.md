# Agent 接手入口与代码地图

目标是在保留现有账号、社团、任务、完成记录和档案的前提下维护 SPS 社团日程。接手时先核对当前请求与部署状态；本系列记录的是 2026 年 11 月 4 日的工程经验，不代替当前仓库指令。

## 先确定正在操作的项目

正式代码仓库是 [SPS-club-schedule/sps-club-schedule](https://github.com/SPS-club-schedule/sps-club-schedule)，前端使用 GitHub Pages，后端使用 Cloudflare Workers 与 SQLite Durable Object。旧微信原型不再是生产入口。

```sh
pwd
git status --short
git branch --show-current
git remote -v
git log -8 --oneline
```

阅读适用的 `AGENTS.md`、`README.md` 和本次涉及的 `docs/`。经验投稿另外受 `experience/AGENTS.md` 约束。若工作区有其他任务的改动，先识别来源；需要独立交付时从已核验的基线建立隔离工作副本。不要用全量暂存把 Android、DNS 资料或别人正在写的功能一并发布。

## 请求如何经过系统

```text
成员浏览器或 Android WebView
  → GitHub Pages 静态页面
  → api.example.org 网关
  → sps-club-api 原 Worker
  → ClubService SQLite Durable Object

持续任务写入
  → booking_sync 待发送版本
  → Durable Object alarm
  → 预约服务固定集成接口
```

自定义域名提供 API；数据库仍在原 API 所属账号。前端公开配置只包含服务地址。本文中的 `api.example.org` 是示例，实际值由当前获授权的部署配置确定。原 API 仍能作为检查与回滚入口，不能因新增网关而顺手重建存储。

## 代码入口

| 文件或目录 | 责任 |
| --- | --- |
| `client/app.js` | 路由、状态和界面操作协调 |
| `client/views.js`、`template-views.js`、`schedule-editor.js` | 任务与模板编辑 |
| `client/workspace.js`、`planner.js` | 电脑布局与大日历 |
| `client/experience.js`、`experience-document.js` | 档案目录、阅读与编辑 |
| `client/onboarding.js`、`shared/onboarding.js` | 成员高亮引导与草稿保护 |
| `shared/domain.js` | 任务、模板、成员等领域操作与授权 |
| `shared/permissions.js`、`assignments.js` | 管理类型与人员解析 |
| `shared/step-dependencies.js`、`backward-schedule.js` | 依赖校验与倒排计算 |
| `shared/sync-client.js` | 增量读取、写后合并、并发响应处理 |
| `shared/calendar.js`、`planner.js`、`ical.js` | 日期、显示范围与 ICS |
| `server/worker.mjs`、`store.mjs` | API 入口、对象与 SQLite 存储 |
| `server/account.mjs`、`admin.mjs`、`archive.mjs` | 认证、账号管理与恢复 |
| `server/booking-sync.mjs`、`experience.mjs` | 预约联动和网页档案 |
| `server/gateway/worker.mjs` | 限定路由的固定上游网关 |
| `scripts/build.mjs`、`experience-files.mjs` | 前端构建、版本清单和档案索引 |
| `tests/`、`qa/` | 自动检查与本地验收资料 |

Android 与外部主讲人功能在本次工作区中还包含未提交文件；部门专项教程已进入 `2dd4df0`。不能假定其他本地模块已进入干净检出的基线。参见[接续清单](https://sps-club-schedule.github.io/sps-club-schedule/#/experience?folder=2026-2027%E5%B1%8A%2F%E7%BD%91%E7%AB%99%E7%BB%B4%E6%8A%A4%2FSPS%E7%A4%BE%E5%9B%A2%E6%97%A5%E7%A8%8B%E5%BB%BA%E8%AE%BE%E4%B8%8E%E4%BA%A4%E6%8E%A5%2F%E7%BB%99Agent%E7%9C%8B%E7%9A%84%E7%BB%B4%E6%8A%A4&document=repo%3A2026-2027%E5%B1%8A%2F%E7%BD%91%E7%AB%99%E7%BB%B4%E6%8A%A4%2FSPS%E7%A4%BE%E5%9B%A2%E6%97%A5%E7%A8%8B%E5%BB%BA%E8%AE%BE%E4%B8%8E%E4%BA%A4%E6%8E%A5%2F%E7%BB%99Agent%E7%9C%8B%E7%9A%84%E7%BB%B4%E6%8A%A4%2F07-%E8%BF%9B%E8%A1%8C%E4%B8%AD%E7%9A%84%E5%B0%9D%E8%AF%95%E4%B8%8E%E6%8E%A5%E7%BB%AD%E6%B8%85%E5%8D%95.md)。

## 修改前确认四种状态

- 工作区里有代码：仅说明本地存在实现。
- Git 中已提交：说明有可追溯版本。
- 工作流和 Worker 部署成功：说明目标环境已接受发布。
- 公开页面和接口回读通过：说明实际使用路径可见结果。

报告中应写明处于哪一步。全套测试数字随版本变化，不用旧 README 中的测试数量替代本次结果。

## 接手后的第一项交付

先用一句话说明问题、预期行为和涉及模块，再为具体变化安排验证。账号和数据库问题必须读服务端；显示问题需检查真实页面；只发布文档则使用档案构建链，不要求额外部署 Worker。
