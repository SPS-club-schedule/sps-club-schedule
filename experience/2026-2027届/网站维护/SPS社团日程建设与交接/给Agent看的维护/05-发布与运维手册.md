# 发布与运维手册

前端、原 API、网关和预约服务具有不同发布入口。只发布经验文档时使用 Pages 链路；改后端时才部署对应 Worker。发布前核对目标账号、仓库与原存储标识。

## 本地启动

使用项目要求的 Node.js 环境，本次基线要求 22 或更新版本。

```sh
npm ci
cp .dev.vars.example .dev.vars
npm run worker:dev
```

已有 `.dev.vars` 时不要覆盖。另开终端：

```sh
npm run build
npm run preview
```

默认前端为 `http://127.0.0.1:4175`，Worker 为 `http://127.0.0.1:8787`，本地数据在忽略的 `.wrangler/`。测试使用本地环境，不把生产凭据复制进演示文件。

## 前端发布

Pages 监听正式仓库 `main`。仓库变量 `API_BASE_URL` 指向 `https://sps-schedule.folderrewind.top`；构建同时生成配置和 CSP。项目路径使用相对资源与 hash 路由。

先审查具体文件，提交本次授权内容，再正常推送。记录提交和工作流结果；不要仅凭 Git push 成功就报上线。若远端已有新提交，先获取、检查差异并正常变基或合并，不强推覆盖他人工作。

## 后端和网关发布

需要后端能力的新功能，通常先部署原 API，再发布使用该能力的前端。涉及新网关路由时，还需在前端发布前完成网关。

```sh
npm run worker:deploy
npm run gateway:deploy
```

这两条命令分别读取 `wrangler.jsonc` 与 `wrangler.gateway.jsonc`。固定账号及已有 Durable Object 绑定，避免多账号登录后误发。网关与原 API 的签名 secret 需匹配，但不在聊天、代码或公开文档中打印实际值。

只新增档案文本不需要执行上述部署。GitHub Pages 工作流也不会自动替你部署 Worker。

## 预约连接变更

先确认接收端兼容，再发布发送端；新接入时由明确绑定的社团 ID 和双方服务密钥控制。需要补齐时使用受保护的集成管理接口，检查旧手动预约与课程保持不变，最后发布需要的新前端。不要用历史数据库导出覆盖当前预约存储。

## 发布经验文档

资料放在 `experience/<届次>/<部门或职责>/<主题>/`。可使用：

```sh
npm run experience:add -- /absolute/path/document.md "2026-2027届/网站维护"
```

辅助脚本只复制，拒绝覆盖，不自动提交。`AGENTS.md` 不进入公开索引；供 agent 阅读的公开资料应使用普通文件名。禁止符号链接、隐藏路径、HTML/SVG 与可执行文件，实际允许列表以 `shared/experience.js` 为准。

本系列用稳定的在线文档地址串联导航。生成链接时对 `folder` 和 `document=repo:<路径>` 分别编码；不要直接把相对 Markdown 链接当成站内在线阅读链接，因为渲染器会按源文件 URL 解析。

构建后对照 `dist/experience-index.json` 核对条数、路径、大小与 SHA-256。上线后从公开索引读取并下载新文档核对 hash，再从“社团经验”实际打开。网页上传清单应一并检查，防止静默重复已有投稿。

## 运维检查与回滚

可从实际允许的调用环境检查：

```sh
curl --fail --silent --show-error --max-time 20   -H 'Origin: https://sps-club-schedule.github.io'   https://sps-schedule.folderrewind.top/health
```

若终端失败但浏览器可用，记录状态、Origin、网络和服务响应后定位，不能仅凭一次请求认定全站宕机。

前端问题可回退到已验证代码并重新走 Pages 构建；若是网关问题，可按原部署说明把 API 构建变量切回原 API，再验证 CORS。回退前检查新旧字段兼容性，尤其是角色、依赖和倒排；回滚页面不会回滚已经写入的数据。

源码包不是生产数据备份。平台恢复、清库和撤销数据需要另行确认范围与恢复点，不能作为普通部署失败的快捷修复。

## 容量与费用

此前做过额度调研和某一天的用量检查，但这些是历史快照。容量应按当前账号套餐、活跃成员、可见页面轮询时长、文件数量与大小估算。网关和原 API 位于不同账号时分别核对，不把额度简单相加。

发布功能数量不是主要计费指标，实际请求、读写、存储和计算才决定消耗。性能优化优先减少空轮询和重复全量读取，再根据当前监控判断是否调整方案。
