# 故障案例与开发经验

这些案例解释本项目为何采用当前规则。接续开发时先复现具体触发条件，再判断经验是否仍适用，不把历史修复当成包治所有同类现象的结论。

## 日历漏活动 应按来源去重

现象是预约页存在手动 SPS 活动，日程页却看不到。原因是早期为了避免日程活动回流，把所有 SPS 社团活动都过滤掉。

修复用保留的生成来源 ID 区分手动活动和同步活动。验证同时包含手动 SPS、其他社团、日程生成副本与课程。这条经验适用于所有跨系统去重：业务名称描述归属，来源 ID 描述同一条记录的来路，不能互相替代。

## DDL 不是活动时间块

用户期待日程同步时，容易把只有截止时间的准备任务也当成预约活动。预约块需要起止时间，只有持续主任务进入同步；添加子任务和填 DDL 并不满足条件。

修复或解释前先检查类型、起止、归档和公开窗口。不要为了“看上去同步成功”替用户捏造一段活动时长。

## 强制刷新会破坏正在做的工作

新版本上线后，旧页面可能还使用旧资源。直接要求每位成员强制刷新，既增加使用成本，也可能丢掉正在写的任务和经验文档。

现在用稳定启动器、内容哈希和版本检查；在表单、上传、保存和教程草稿存在时延后更新。新增入口也必须接入草稿保护。验证要在编辑过程中模拟新版本，确认草稿保留，再离开编辑状态确认升级发生。

## 教程需要贴着真实界面走

初版文字弹窗没有满足用户对实际操作演示的期待，于是改为高亮真实控件并压暗周边。再加入“上一步”后，必须处理跨页面草稿恢复和重复添加子任务。

经验不是“教程越长越好”，而是每一步指向真实控件，说明当前操作及后果。演示导航不应误保存模板、发布任务或上传资料。教程完成状态、版本更新暂停与编辑草稿要一起考虑。

## 数据关联使用稳定 ID

模板角色和依赖需要经历改名、排序、复制、删除。若用角色名或步骤位置绑定，调整顺序就可能把工作分给错误的人。

当前使用稳定角色与步骤 ID，复制或发布时明确映射到新对象。删除时清理引用，旧客户端无法保留结构时提示刷新。测试应包含关系变化，不能只测第一次保存。

## 并行分支不能把耗时简单相加

倒排中，一个前置节点可能服务多个后续节点。它的截止是各下游最晚开始的最小值；两个互不依赖的分支不需要把工期串起来。

验证通过独立的路径约束计算对照结果，并改变输入顺序。仍需明确边界：算法没有人员负荷调度，不处理工作日，也不把建议开始变成日历活动块。

## 数据库行序不是业务关系

依赖功能的一次工作流暴露了夹具依赖 SQLite 返回顺序的问题。修复使用稳定业务标识进行断言，保留领域实现的真实语义。

本地一次通过不能替代干净环境的 CI；CI 失败也不能自动推断业务逻辑坏了。先看失败断言与数据选择方式，再定位。

## 改域名不必搬数据库

接入另一个 Cloudflare 账号的域名时，用户明确选择保留账号与任务数据库。固定上游网关满足入口需求，减少了数据迁移范围。

运维经验是把“换入口”“换运行代码”“迁移持久化数据”分别描述。尤其不能因重命名 Worker、绑定或对象而让系统看似出现空数据库，再误导用户重新注册。

## 公开档案与内部操作材料应分清

经验档案已选择公开可读。给 agent 的资料同样公开，不能因为受众是程序就放入恢复码、token、真实邀请或私人成员信息。

只写必要的配置名、命令结构和验证方法，实际密钥留在对应环境。网页和 Git 两个存储来源要保持可追溯，整理旧文档前查重复，不用复制所有本地文件代替经验写作。

## 持续交付保留三个事实

每项工作都应留下问题与目标、最后实际实现、验证及尚未覆盖的范围。遇到被中断的任务，先读当前 Git 与运行环境，再续上剩余部分；不要依据“上次说完成”重做发布，也不要把未提交工作当成无用文件清掉。
