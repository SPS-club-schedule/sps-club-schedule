# 测试与验收流程

验证应证明用户关心的行为和数据保持成立。单元测试、真实 Worker 与 SQLite 检查、浏览器验收各自覆盖不同问题，不互相替代。

## 项目现有检查

```sh
npm test
npm run test:worker
npm run test:gateway
npm run build
git diff --check
```

Pages 工作流会运行三套自动测试并构建。应用测试覆盖领域、算法和界面辅助逻辑；Worker 集成测试使用本地运行时和 SQLite；网关测试覆盖转发边界。测试不应写入生产社团。

每次记录对应提交及实际通过数量。历史文档里不同数字代表不同阶段，一些本地统计还包含当时未提交的 Android 测试，不能直接作为远端工作流预期数量。

## 按变更挑选验证

| 变更 | 关键证据 |
| --- | --- |
| 模板或分工 | 保存、重开、复制、排序、删除关系、实际发布结果、旧客户端保护 |
| 倒排算法 | 多分支与中间约束、分钟精度、过去开始拒绝、与独立计算结果比较 |
| 账号与权限 | 不同角色、同级/越级、跨社团、版本冲突、密码错误和权限撤销 |
| 同步与归档 | 晚到响应、重试、切换身份、归档后恢复与重新归档 |
| 日历与 ICS | 跨日跨月、午夜、自己与他人的分工、文本转义、实际导入边界 |
| 文档发布 | 类型和路径校验、索引条目、正文 hash、线上阅读和导航 |
| 布局或教程 | 电脑与窄屏、真实控件定位、上一步、草稿保留、误提交保护 |

只改文档时，不为每段 prose 编写重复实现的单元测试；使用现有构建、渲染及链接检查即可。

## 一个可复用的本地验收

在隔离数据中建立虚构社团及不同角色成员。创建模板，选人并设置日期，保存重开确认；再套用发布，逐个查看生成的子任务和负责人。切换另一成员查看待办，记录一次完成和撤销，检查同步；最后归档及恢复。

浏览器应操作实际按钮而不是只读静态 HTML。电脑看窄工作台和宽面板是否独立滚动；手机以约 375—390 px 宽度检查表单、表格、弹窗和滚动。截图不应包含真实密码、恢复码或成员敏感资料。

## 倒排的独立校验

已做过的测试将多个七节点无环图与穷举下游路径约束比较，并反转输入顺序检查结果。这个方法能发现错误求和、错误取 max 或依赖数组顺序，而不只是复写同一个递归函数。

至少保留用户的 3/1/1 天文案—海报—宣传例子，并验证多前置、共享前置、中间提前约束、独立分支、零耗时、自定义截止及旧模式。发布结果应与预览一致，实际 SQLite 重启后仍一致。

## 曾经失败的 CI 给出的教训

依赖功能的一次 Pages 工作流失败，后续提交 `61b38e1` 修复了模板运行时测试对 SQLite 行返回顺序的依赖。数据库没有显式排序时，测试应按稳定 ID 或明确键比较；只有排序本身是需求时才断言顺序。不能为让夹具通过而改变正确的业务关联。

## 发布后再验证一次

确认目标提交的工作流成功，读取正式配置、版本与档案清单，并在真实入口打开关键页面。对业务变更，优先采用不会污染生产的只读检查；需要生产样例写入时，按当前任务明确范围处理。

“服务返回 200”不能证明资料目录正确，“构建成功”不能证明页面读取了新版本，“模拟器通过”不能证明所有手机可用。最终交付只陈述实际验证到的范围。
