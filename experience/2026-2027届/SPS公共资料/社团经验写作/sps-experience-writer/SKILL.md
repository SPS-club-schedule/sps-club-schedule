# 写一份下一届能用的 SPS 社团经验

用中文访谈，一次问一个当前最需要弄清的问题，等成员回答后再追问。成员在开场已经讲过的内容直接记下，把时间留给缺失的细节。

## 先确定这件事有没有旧档

第一问是“这是一个什么任务？”。如果描述过于笼统，追问实际要交付什么。一旦能识别任务，就先查 [SPS 经验档案](https://sps-club-schedule.github.io/sps-club-schedule/#/experience)。用任务名、活动别称、产出物或相关职责跨届次搜索。查目录、文件名和说明，再打开最接近的正文，核对目标、时间和工作范围。

网页把两种来源合在一起。用程序查询时，两份公开清单都要读，无需登录。

- [仓库投稿清单](https://sps-club-schedule.github.io/sps-club-schedule/experience-index.json)的文件在 `entries` 中。将条目的 `path` 按段进行 URL 编码，接在同站点的 `experience/` 后即可读取。
- [成员网页投稿清单](https://sps-schedule.folderrewind.top/experience)的文件在 `data.entries` 中。用同一服务的 `/experience/files/<id>` 读取。若服务地址变更，从[站点配置](https://sps-club-schedule.github.io/sps-club-schedule/config.json)读取 `apiBase`。

有相近资料时，给出旧档标题、链接及相似点，问“这是你说的同一个任务吗？” 有多个候选就让成员辨认。确认是同一任务后，读原有成员版和 Agent 版，记下应改的具体章节。沿用原目录和原稿，保留仍适用的经验，交代这次增补或改了什么。两版中原来缺哪版，才按本次参与情况补哪版。成员确认是不同任务，或两处均已查过且没有候选时，再新建主题。一处查询失败就标明查到了哪里，可以继续访谈、留本地草稿，正式建档前补查。

## 问清谁负责、Agent 做过什么

问“这项任务主要由哪个部负责，还是 SPS 集体负责，或是个人负责？” 记录主责，涉及合作时再问谁协助、交接点在哪。目录名表示资料放在哪，负责归属以当事人回答为准。个人负责可直接写“个人负责”，无需索取实名。

再问“执行这项任务时，有 Agent 参与吗？” 本次帮忙整理文字与当时参与执行要分开。

- **有参与**。按任务关键词、项目、时间段定位执行时的 session。在 Codex 可先筛选聊天列表，再读相关聊天及其接续记录。提取 Agent 实际负责的部分、关键决策及理由、失败尝试、实际采用的步骤和验证结果。对照当时的交付物、代码或配置核实结论，区分当时做成了什么和现在运行的是什么。只读有关任务的记录。
- **找不到相关 session 或无法读取**。先索取能定位它的标题、日期或成员愿意提供的节选。仍缺失时，用现有材料写 Agent 稿，注明哪些是当事人回忆、哪些细节待核实。公开文档只保留交接所需的事实和可分享的证据，不贴聊天原文、私人聊天链接、凭据或个人路径。
- **没有参与**。只写成员经验，跳过会话检索和 Agent 稿。

## 把每个难点问到能交接

问“你在这个任务中遇到了哪些主要难点？” 如果成员一次提了几个，先记下顺序，从第一个问“当时卡在哪一步？你最后是怎么解决的？” 跟着回答补齐真正缺的细节：看到了什么现象、试过什么、为什么换办法、具体改了什么、怎么知道有效。听到“解决之后又发现……”时，把新问题单列，接着追问。问清一项或记为待解决后，再进入下一项。成员说没有遇到难点就如实记录。

例如，成员说自己负责社团日程网站建设，Agent 参与，费用和直连访问都遇到过问题。先在档案中找到《SPS社团日程建设与交接》，请成员确认。费用这一项可追问“你当时用的是 Cloudflare 的哪项免费资源？凭什么判断够社团使用？” 接着单问“换到 Cloudflare 以后，在哪种网络下遇到了什么现象？” 若成员已说明默认 Workers 域名需要代理、自有域名可直连，就追问“换过入口后，你关掉代理做了哪个操作来确认恢复？” 把测试环境、时间和实际结果写入相应难点。只有观察到哪个域名、哪种网络的结果，就把结论写到那个范围；未提供的额度数字和验证结果留待核实。

## 写稿与交付

**给成员看的经验**要让下一位接手的人知道任务交付什么、由谁负责、Agent 参与了哪部分、实际按什么顺序做。每个难点单列一小节，用成员听得懂的语言写清现象、选择该办法的理由、照做的步骤、成功的判断方法和遗留问题。例如，说明当时为什么选免费资源，后来又为什么换访问入口，以及普通成员怎样判断自己已经连上。

**给 Agent 看的技术交接**在有 Agent 参与时单独成文，与成员版互相指引。两版覆盖同一组难点，保留相同的主责、因果顺序和解决状态。Agent 版在每个难点下补足接手所需的信息，例如输入与产物、复现前提、相关文件或服务、实际命令与配置项、失败表现、修复和验收步骤。写清应看到的结果，以及哪一步已经验证。技术细节以 session 或实际交付物为据，示例命令里的秘密用占位符。非编程任务同样可记录素材格式、操作顺序、输出样例和人工复核点。

交付前逐项对照访谈与旧稿，检查每个难点的解法和证据是否都能在对应文档中找到。未解决或未经验证的事项写明现状和下一步。给成员列出新建或更新的文件、具体章节及待核实处。

按成员请求决定是否公开。需要发布时，仓库稿依照 `experience/AGENTS.md` 修改原路径，网页稿由有权限的人编辑原条目；若版本变了，重读再合并。没有原稿写权限时，交付可并入指定章节的改稿。新主题放入实际届次与职责对应的目录。发布后，从公开档案重新打开资料，核对正文和链接。
